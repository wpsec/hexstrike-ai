# HexStrike AI 代码规范（中文）

## 1. 目标与范围

本规范用于统一 `hexstrike_server.py`、`hexstrike_mcp.py` 及后续模块的代码风格，目标是：

- 提升可读性、可维护性与可审计性。
- 降低安全工具编排与命令执行中的误用风险。
- 保证 AI 代理调用链路可追踪、可观测、可回溯。

---

## 2. Python 与依赖约束

- Python 版本：`3.8+`（建议在 `3.10+` 验证）。
- 新增依赖必须在 `requirements.txt` 明确声明。
- 依赖升级需说明兼容性影响与回滚方案。

---

## 3. 基础风格

- 遵循 PEP 8，统一使用 4 空格缩进。
- 单行长度建议不超过 100（超长命令或正则可例外）。
- 导入顺序：标准库 -> 第三方库 -> 本地模块。
- 避免无意义缩写，命名要表达语义。

命名约定：

- 变量/函数：`snake_case`
- 类名：`PascalCase`
- 常量：`UPPER_SNAKE_CASE`
- 私有辅助函数：前缀 `_`

---

## 4. 类型标注与文档字符串

- 新增/修改函数应补充类型标注。
- 对外接口（Flask endpoint、MCP tools、核心 manager）必须有文档字符串。
- 文档字符串推荐结构：用途、参数、返回值、异常/副作用。

示例：

```python
def safe_post(endpoint: str, json_data: Dict[str, Any]) -> Dict[str, Any]:
    """向后端 API 发送 POST 请求并统一处理异常。"""
```

---

## 5. 日志规范

- 使用 `logging`，禁止在核心逻辑中直接 `print`。
- 日志级别：
  - `DEBUG`：调试细节（请求参数、分支命中）。
  - `INFO`：关键流程里程碑（任务开始、结束、状态切换）。
  - `WARNING`：可恢复异常或降级行为。
  - `ERROR`：请求失败、工具执行失败。
  - `CRITICAL`：安全风险、不可恢复故障、需要人工介入。
- 日志中避免泄漏敏感信息（token、cookie、密钥、凭据明文）。

---

## 6. 异常与错误处理

- 外围接口必须捕获可预期异常并返回结构化错误。
- 避免裸 `except:`，优先捕获具体异常类型。
- 失败返回统一包含：`success`、`error`、必要上下文字段。
- 可恢复场景优先提供 recovery 信息，而不是直接中断流程。

---

## 7. 命令执行与安全

- 命令参数优先使用白名单/枚举值，禁止直接拼接不可信输入。
- 必须限制执行超时，防止长时间阻塞。
- 对高风险参数（如 shell 特殊字符）先做过滤或转义。
- 记录执行命令时仅打印必要信息，避免输出敏感数据。
- 能用结构化 API 调用时，优先替代原始 shell 命令。

---

## 8. Flask API 设计

- endpoint 命名应语义明确、分层一致：`/api/<domain>/<action>`。
- 请求参数要有默认值与类型兜底。
- 返回 JSON 结构建议统一：

```json
{
  "success": true,
  "data": {},
  "error": null,
  "metadata": {}
}
```

- 长耗时任务建议异步化或提供进度查询能力。

---

## 9. MCP Tool 设计规范

- 每个 `@mcp.tool()` 方法应保证：
  - 参数可理解（名称/默认值合理）。
  - 错误可观测（日志 + 结构化返回）。
  - 输出可消费（结果字段稳定）。
- 同类工具应复用公共 helper，避免重复逻辑。
- 业务逻辑与展示逻辑（颜色、UI 文本）尽量解耦。

---

## 10. 注释规范（中文）

- 注释以“解释原因和约束”为主，不重复代码字面含义。
- 优先在复杂逻辑前写块注释，而不是行尾密集注释。
- 关键安全分支、恢复策略、兼容性处理必须有中文注释。
- 保持注释与代码同步，变更代码时同步更新注释。

推荐写法：

```python
# 这里先做轻量健康检查，避免在主流程里因连接失败阻塞太久
```

不推荐写法：

```python
# 给变量赋值
value = x
```

---

## 11. 测试与验证

- 代码变更至少进行以下验证：
  - 语法检查：`python3 -m py_compile`（或等效）。
  - 核心启动验证：`hexstrike_server.py` 能正常启动。
  - 关键接口 smoke test：`/health`、至少一个工具 endpoint。
- 新增功能建议补充最小可复现测试步骤。

---

## 12. 提交与评审建议

- 提交信息建议格式：`type(scope): summary`。（中文描述）
  - type：`feat`（新功能）、`fix`（修复）、`docs`（文档）、`refactor`（重构）、`test`（测试）、`chore`（其他）。
  - scope：影响范围，如 `api`、`mcp`、`core`。
  - summary：简要描述变更内容。
- 单次提交聚焦单一主题（文档、注释、功能变更分开）。
- PR 描述至少包含：变更内容、风险点、验证方式、回滚策略。

---

## 13. 文档落地目录约定

- README 相关：仓库根目录（如 `README.md`、`README.zh-CN.md`）。
- 其他项目文档：统一放在 `docx/` 目录。
- 新增专题文档命名建议：`<TOPIC>.zh-CN.md`。
